# Why this ESLint config is scoped the way it is

There was no ESLint config at all before this. That is worse than no linter: `next lint` with no
config prompts for one, the prompt throws on a non-TTY runner and exits 1 having linted nothing,
and on a runner that does have a TTY it blocks. So the gate was guaranteed red and told you
nothing.

The scope mirrors `backend/ruff.toml`: rules that catch bugs, not rules that argue about style.
`next/core-web-vitals` brings the react-hooks rules, which are the highest-value checks in this
codebase, plus the Next-specific correctness rules.

Adding it immediately found a real defect: `useMemo` called after an early return in
`components/console/console-window.tsx`. React maps hook state by call order, so a render where
`consoleInstance` was null skipped that hook and the next render called one more than the
previous one. That either throws "Rendered more hooks than during the previous render" or hands
the memo another hook's slot.

Two rules are off, both deliberately and both temporarily:

- `react-hooks/exhaustive-deps` — around 200 pre-existing violations. Turning it on now makes
  the gate red on day one, which is how a lint gate becomes something people skip. Land it with
  the cleanup in the same commit.
- `react/no-unescaped-entities` — 8 violations, all literal quotes and apostrophes in visible
  copy. It is a style rule, not a bug rule, and mechanically rewriting user-facing text to
  satisfy it is churn with a real chance of changing what an operator reads.

Run it with the local binary, not `next lint`:

    cd frontend && ./node_modules/.bin/eslint src --ext .ts,.tsx

`next lint` is deprecated in Next 15 and passes eslintrc-era options that newer ESLint rejects,
so it fails for reasons that have nothing to do with your code.
